Policy Cards · OpenProse spike

When a policy changes, redo only what moved

Policy Cards turns long procedural documents into reviewed, agent-ready cards. OpenProse is the runtime model that keeps that card set current: every step declares what it needs and what it maintains, a step re-runs only when something it watches changes, and every run leaves a receipt.

The problem it solves

Decomposition is not a one-off job

Policies are reissued. Thresholds move, definitions are reworded, notices come and go. If every new version means re-running the whole decomposition, reviewers re-approve hundreds of cards they already checked, and nobody can say afterwards why a card changed.

What people need is narrower: tell me which cards this version actually affects, why, and keep a record. That is a runtime problem, and it is the problem OpenProse's responsibility runtime was designed for.

Where it fits

OpenProse runs the pipeline; Policy Cards defines what good looks like

OpenProse owns how the work runs

  • Steps written as contracts: what each needs, what it keeps true
  • Deciding what changed by comparing fingerprints, never by asking a model
  • Skipping steps whose inputs did not move
  • Receipts: an append-only record of every step in every run

Policy Cards owns what a good result is

  • The card contract and four card types
  • The validator that blocks any card that breaks the contract
  • The review application and approval rules
  • The published artifact format agents consume

Vocabulary

OpenProse terms, in Policy Cards language

responsibility
A standing step that keeps something true: the passages, the policy map, the card set, the review queue.
gateway
How a new policy version enters. Re-sending the same version does nothing.
facet
A named part of what a step maintains, such as parameters or slots. Other steps subscribe to facets, not to everything.
fingerprint
A hash of a facet's meaningful content. Same hash, nothing changed; the same idea as a card's content hash.
memo key
The step's own contract plus the fingerprints it watches. Unchanged key, skip the step.
render
One run of a step. For the map and cards this is model work; for structure and the queue it is plain code.
postcondition
What must hold before a result is saved. Here it is our validator, so a bad card is never committed.
receipt
The record of one step in one run: what woke it, what it saw, what moved, what was reused. The audit trail.
Why it makes this more usable

What changes for each person

Policy reviewer

BeforeEvery new version reopens the whole card set.

AfterA queue of only the affected cards, each with a reason: changed, parameter changed, or a card it depends on moved.

Policy owner

BeforeAmbiguities found during decomposition get lost between versions.

AfterEach version's map carries its issues forward, and new wording raises new ones (for example "and/or" in a ratio's denominator).

Risk and audit

BeforeHard to show why a card changed or who checked what.

AfterA receipt per step per run: the inputs seen, what moved, what was reused, and every rejected render with the reason.

Platform and cost

BeforeModel work scales with document size on every run.

AfterModel work scales with what changed. Unchanged versions cost nothing; a one-clause change rewrites one or two cards.

What the spike taught us

Findings

  • Stable passage keys are the real work. Removing one notice at the top of a real section renumbered 140 passages. Keys carried by matching clause and text kept 139 of 142 stable, so only true changes were flagged.
  • Skipping happens at two levels. OpenProse decides per step; inside the cards step a per-card check (the slot, the passages it cites, the parameter values it uses) turns "the cards step ran" into "one card was rewritten".
  • A threshold change can leave a card's text identical. Cards say {{DTI_MAX}}, not "45%". The fix: each card carries the values of the parameters it uses, so the change moves the card's fingerprint and reviewers see it as "parameter changed".
  • Watching two sources can mix versions. When the queue watched both cards and parameters, a failed card update still woke it with half-new data. Watching only the cards closed that gap.
  • The validator has to be code. Contract conditions are written in prose; our validator is what actually stopped a card with a reworded quote.
  • Adopt the model, not the dependency yet. The language is young (its last major update changed the vocabulary without a data migration), the reference runtime is alpha, and the default model gateway would need review before regulated text goes through it.
Try it

Run it yourself

From the repository, on the spike/openprose branch:

npm run spike:openprose

It resets its own state, runs the four runs above and writes spikes/openprose/demo/report.html. The contracts are in spikes/openprose/src/policy-cards/; receipts land in local/demo-root/state/world-model/<step>/receipts.jsonl.

To see OpenProse's own tooling, install its skill into Claude Code and ask the session to compile our contracts:

npx skills add openprose/prose
prose compile spikes/openprose/src/policy-cards

The second command is typed into a Claude Code session, not a shell: OpenProse has no binary, the agent session acts as its runtime.
